# Spec: aes67-srt — AES67 over SRT

Status: **draft for review.** The frozen decisions below were settled in an interview with the
project owner (2026-09-16). The **open items** at the end still need answers before commissioning.

**Mostly built.** The wire format (`wire`), the SRT transport (`transport`), the audio device
abstraction with its null and ALSA/RAVENNA backends (`audio`), the `aes67-daemon` REST client with its
fake (`daemon`), the engine that joins them, the `clock` (playout buffer, ratio control, resampler)
and the `delay` (A/V offset and impulse test signal) exist and are tested on Linux CI and macOS, with
the research in `docs/research/` and the decisions in `docs/adr/`. **Audio has flowed through this
program on hardware** — a Pi 5, 64 channels, the RAVENNA device, 0 refused (issue #18). **What remains
is the control surface (`http`, the web UI) and the `app` hardening**, and the one figure no lab run
has produced: the ppm offset between two real appliances across a WAN (issue #10).

## Goal

A Pi-class Linux appliance that extends a production site's AES67 fabric to a remote location
over the public internet: **64 channels (eight 8-channel blocks) of uncompressed L24 PCM at
48 kHz in each direction**, carried in **a single SRT stream per link**, with the same binary
acting as transmitter, receiver or both. Nobody listens to the audio in the path — the far end
is equipment (a console, a DAW, monitors, a transmitter) on its own AES67/Dante LAN with its
own PTP domain. An operator configures it from a web UI with no shell access, because it ships
to other people's sites.

## What this is

```
 SITE (production)                                  REMOTE
 ┌────────────────────────────┐                 ┌────────────────────────────┐
 │ Dante / AES67 devices      │                 │ Dante / AES67 devices      │
 │ 8 x AES67 streams, 8ch     │                 │ 8 x AES67 streams, 8ch     │
 │ 1 ms ptime, PTP, SAP/mDNS  │                 │ 1 ms ptime, PTP, SAP/mDNS  │
 └──────────┬─────────────────┘                 └───────────────▲────────────┘
            │ AES67 / RTP L24 48 kHz, multicast                  │
 ┌──────────▼───────────────────────┐         ┌─────────────────┴──────────┐
 │ aes67-daemon  REST :8080, PTP     │         │ aes67-daemon  REST :8080   │
 │ RAVENNA ALSA  plughw:RAVENNA 64ch │         │ plughw:RAVENNA 64ch        │
 │ ───────────────────────────────── │         │ ────────────────────────── │
 │ aes67-srt appliance               │         │ aes67-srt appliance        │
 │  ingest → blocks → frames ────────┼──SRT────┼─→ clock → delay → egress  │
 │  egress ← delay ← clock ◄─────────┼──SRT────┼── frames ← blocks ← ingest │
 │  web UI + REST API :8082          │         │ web UI + REST API :8082    │
 └───────────────────────────────────┘         └────────────────────────────┘
```

Both ends run the same software. Either end can transmit, receive or do both at once; the role
is configuration, not a build variant.

## Why the existing tools do not cover this

- **Public SRT tooling** (`srt-live-transmit`, `srt-tunnel`, ffmpeg's SRT I/O) moves bytes
  reliably, but knows nothing about AES67 channel blocks, the daemon's channel map, or A/V
  alignment. Gluing them together means a bespoke arrangement per site and no UI.
- **`aes67-sip`** (sibling) already proves the AES67 half — daemon REST client, RAVENNA/ALSA
  backend, resampler, ring buffers, polling web UI, one-command installer. But its WAN path is
  SIP + G.722 for intercom: one mono channel per line, lossy by design, and a call model we do
  not want. None of it carries 64 channels of PCM.
- **`AES67-VSC`** (sibling) is a Windows endpoint, not a transport.
- **Hardware codecs** (Haivision/Telos/Comrex class) do SRT audio, but with a small fixed
  channel count, a closed control surface, and a price per site.

## Constraints established by research — not assumptions

| Established fact | Where from | Consequence here |
|---|---|---|
| **AES67 allows ≤8 channels per stream**, 1 ms packet time, 48 kHz, L16 mandatory / L24 optional, PTPv2 (IEEE 1588-2008) media profile, DSCP EF(46)/AF41(34) | `AES67-VSC/.scratch/virtual-sound-card/spec.md` (researched there) | "Blocks of 8 channels" is **not a design choice — it is the AES67 stream size.** 64ch means 8 AES67 streams per direction at each end, and the block is the natural mapping unit for everything downstream |
| `aes67-daemon` (bondagit) exposes REST on `:8080`: sinks, sources, config, PTP status, browse (`all`/`mdns`/`sap`), source SDP; **up to 64 channels** | `aes67-sip/docs/api.md` §6, `DECISIONS.md` #11 | We never speak RTP or SDP ourselves. The daemon owns discovery, subscription and PTP; we own PCM and SRT |
| The daemon's audio appears as an ALSA device **`plughw:RAVENNA`** (Merging RAVENNA driver, DKMS kernel module) | `aes67-sip/docs/DECISIONS.md` | The PCM seam is ALSA, and 64 channels on one device is already what the daemon offers |
| Without a PTP grandmaster on the VLAN the RAVENNA device **never locks and no audio flows** | `aes67-sip/docs/DECISIONS.md`, open item 4 | Both ends need a locked PTP domain. This is a preflight check in our UI and a commissioning blocker, not an edge case |
| The daemon's source payload is configurable per stream: `L24` (default, Dante interop), `L16`, `L2432`, `AM824`, `L32` | `aes67-sip/docs/api.md` §5 | L24 is the interop choice; the wider payloads exist if we ever need them |
| **libsrt is MPL-2.0** — file-level copyleft that does not extend to the larger work | verified — `docs/research/libsrt.md`, ticket 02 | Unlike `aes67-sip`, where PJSIP + the daemon forced GPL, **our licence is a choice, not an obligation.** Decided as GPL-3.0 for suite consistency (ADR 0002) |

Everything marked *unverified* is a research ticket, not a fact. Do not build on it until it has
a source.

## Decisions frozen by interview

| # | Decision | Where it lands |
|---|---|---|
| 1 | **64 channels each direction** — eight 8-channel blocks, L24, 48 kHz, PCM | `audio.channels: 64`, `link.blocks: 8` |
| 2 | **One SRT stream per link, bidirectional**; roles are configuration, not variants | `link.role: tx \| rx \| duplex` |
| 3 | **The same binary at both ends**; TX/RX/both chosen in config and UI | no build variants, no second product |
| 4 | **Pi-class Linux appliance**, one-command install, shipped to other people's sites | `scripts/install.sh`, systemd unit |
| 5 | **Public internet, both ends NAT'd** — SRT caller/listener/rendezvous and passphrase encryption must come up unattended | `link.mode`, `link.passphrase` |
| 6 | **Never drop audio the timeline can use.** SRT discards only packets that arrive after their play time (too late to play at all) — leaving that off head-of-line blocks and kills the link. When the link sags, delay grows, the UI shows the delay, and it alarms past ~500 ms | `link.alarm_delay_ms: 500`; `TLPKTDROP` on; playout owns the timeline |
| 7 | **100–200 ms nominal transport delay** (SRT latency ~120 ms) — low enough to leave room to delay audio into A/V alignment | `link.latency_ms: 120` |
| 8 | **A/V alignment is ours on the audio side**: a live, glitch-free delay offset plus an impulse/clap test signal | `egress.delay_ms`, test-signal generator |
| 9 | **v1 is PCM only, but the wire format is codec-ready** — payload type per block, codec seam in the pipeline | `wire` frame header |
| 10 | **Opus/AAC are roadmap phase 2**, not out of scope | `docs/ROADMAP.md` |
| 11 | **`aes67-daemon` is a black box** reached over REST: no fork, no upstream code reuse, we own our control surface | ADR (precedent: `AES67-VSC` ADR-0005/0006) |
| 12 | **Each end keeps its own PTP domain**; we rate-adapt between them rather than tunnelling PTP | `clock` module |
| 13 | House stack and deployment model copied from `aes67-sip`, not reinvented | C++17/CMake, own REST API + polling UI, JSON config, systemd, `tests/` |

### How decisions 9 and 10 reconcile with the interview's wording

The interview recorded the constraint as *"no lossy codec at any point, ever"*. That sentence was
aimed at **behaviour** — nothing may degrade the audio by itself — and not at the project's ceiling.
This is the reconciliation, written down so the two cannot drift apart again:

- **In v1 the appliance encodes nothing lossy.** PCM in, PCM out. No exceptions, no escape hatch,
  and `opus`/`aac_lc` in the `PayloadType` enum are **reserved values, not wired to any encoder**.
- **The wire format reserves a per-block payload type** so a codec can be added later as a
  format-compatible addition. Omitting the field would make adding one a breaking change, and every
  appliance already sitting in another building would have to be re-flashed in lockstep — a migration
  that never happens cleanly. The field is cheap; the migration is not.
- **The invariant that is permanent, in every phase: quality changes only when a human changes it.**
  No adaptive bitrate, no automatic quality reduction; `TLPKTDROP` is on only because a packet past its
  play time cannot be played, and dropping it is not a quality change but the only alternative to the
  link stalling — in codec mode exactly as in
  PCM. This invariant, not the codec ban, is what the interview was protecting.

Whether the enum carries those reserved values in v1 at all is the `wire` module spec's decision;
what is settled here is that the *frame layout* has room for them.

## Decisions of record

- `docs/adr/0001-own-wire-format-over-srt.md` — our own frame format in the SRT stream rather than
  RTP-over-SRT, one sample position per frame, payload type per block. Amended by ticket 02: a frame
  does not fit in one SRT message.
- `docs/adr/0002-licence-under-gpl-3-0.md` — **accepted**: GPL-3.0, for consistency with the sibling
  appliance. libsrt is MPL-2.0 and obliges us to nothing, so this was a choice; `LICENSE` carries the
  canonical text.
- `docs/adr/0003-clock-reconciliation-by-resampling.md` — **accepted**: continuous resampling rather
  than slipping samples, because at 10 ppm corrections arrive every two seconds and 11% of a Pi core
  buys the removal of that requirement entirely.

**Resolved** (ticket 06): the enum *does* carry the reserved values in v1, and a PCM-only build
refuses them at decode with a message that says so ("not supported by this build") rather than
misreading them as PCM. A byte that is not a payload type at all is reported differently ("unknown
payload type N"), because "upgrade the appliance" and "find the broken cable" are different
instructions for whoever is standing in front of it.

## Capability map

Gated: module boundaries, dependency direction and build order are reviewed **before** any module
spec is written.

| Module id | Responsibility | Depends on |
|---|---|---|
| `wire` | The frame format: header (version, link id, sequence, sample position, block count) plus block payloads with per-block payload type. Pure, no I/O, fully unit-testable. | — |
| `transport` | The libsrt link: listener/caller/rendezvous, plus an in-process `loopback` that needs no library or socket so the whole audio path runs on a machine with nothing attached. One duplex connection, latency and passphrase settings, link statistics (RTT, loss, retransmits, bandwidth, buffer delay). | — |
| `audio` | ALSA capture and playout on `plughw:RAVENNA`: 64ch @ 48 kHz, period sizing matching AES67's 1 ms ptime, ring buffers between the ALSA cadence and the frame cadence. Null backend for macOS and CI. | — |
| `daemon` | REST client for `aes67-daemon` on `:8080`: sinks, sources, PTP status, discovery, source SDP. Full fake implementation for tests. | — |
| `clock` | **The hard module.** Recover send timing from the SRT stream, rate-adapt to the local PTP domain, hold all eight blocks at one sample position, schedule playout. | `wire`, `audio` |
| `delay` | The A/V delay line: live, glitch-free offset adjustment, and the impulse/clap test signal. | `clock` |
| `control` | Our own REST API and static web UI: link configuration, block/channel mapping, live delay and levels, link statistics, commissioning preflight. | all of the above |
| `app` | Supervisor: config file, role wiring, logging, systemd unit, commissioning loopback (transmitting to ourselves). | `control` |

**Build order:** `wire` + `transport` (loopback on localhost — no audio, no daemon) → `audio` +
`daemon` (real daemon, one box, commissioning loopback) → `clock` → `delay` → `control`/UI →
`app` hardening.

Dependencies point one way and there are no cycles. Contracts between modules belong to the
provider's spec; `control` is a facade over the rest, which is why it depends on all of them.

## Shape

**The 8-channel block is the unit everywhere.** It is the AES67 stream size (≤8ch per stream),
which is why "blocks of 8ch" is a requirement rather than a design choice: a 64-channel link is
8 AES67 streams per direction at each end, and 8 blocks per wire frame.

**The wire frame.** One header, then the block payloads:

| Field | Purpose |
|---|---|
| version, link id | Format evolution and multi-link addressing |
| frame sequence | Ordering and loss accounting |
| **sample position** | 48 kHz frames since stream start — **the sync anchor** |
| block count | 1–8 today |
| per block: index, **payload type**, channel count, payload bytes | `0` = L24, `1` = L16, `2` = Opus, `3` = AAC-LC reserved. This field is what makes phase 2 possible |
| CRC32 | Catch corruption rather than play it |

**Why our own format instead of RTP-over-SRT.** RTP would add a second, unnecessary timebase to
reconcile (SRT is already reliable and ordered) and cost a header per 8-channel stream. One sample
position covering the whole frame is exactly the cross-block sync guarantee required: blocks in a
frame are sample-aligned **by construction**, not by reconciliation. SRT's own stream semantics are
now **verified** (`docs/research/libsrt.md`), and one of them changes the transport rather than the
format: live mode caps a single send at **1316 bytes**, so **a frame spans about eight SRT
messages** and ticket 07 fragments and reassembles. Because SRT orders messages but does not promise
they all arrive — `TLPKTDROP` drops the message carrying a period that came too late — **each message
carries an 8-byte fragment header**, so the receiver sees the loss and gives up only that frame
instead of desyncing the stream (ADR 0001's second amendment, 2026-09-18). Bonding turns out to be a
compile-time option that is off by default and incompatible with rendezvous, which keeps redundancy
out of v1 for a better reason than "not yet".

**Clock and rate adaptation — the hard problem, named honestly.** SRT delivers reliable bytes, not
a clock. Both ends' `plughw:RAVENNA` devices are driven by *their own* PTP grandmaster, so the two
sample clocks differ by however many ppm their crystals differ. Left alone, the receiver drifts
against the sender and eventually overruns or underruns — heard as a click every few minutes, or
worse. Options, none free:

| Option | Cost | Risk |
|---|---|---|
| **Adaptive playout buffer**, slipping a sample at a signal zero-crossing or through a short crossfade | No continuous DSP; one inaudible discontinuity every few minutes | The slip must be rare enough to be inaudible across 64 channels, and provably drift-free |
| **Continuous asynchronous sample rate conversion** (fractional ratio) | Every sample processed on all 64 channels — a real Pi CPU budget question, plus a quality claim to defend | Easier to reason about, expensive to run |
| **Tunnel PTP / lock the far end to us** | Needs PTP across a public internet, which is exactly what cannot be relied on | Rejected by decision 12; the far end keeps its own domain |

Ticket 02 (issue #3) answers this with a measurement rather than an argument.

## Audio path and levels

- **48 kHz only in v1.** L24 (`s24_3le`), with `s16_le` available as a configuration choice — **not
  as an automatic fallback.** This bullet originally said "automatic fallback, matching
  `aes67-sip`", and the ALSA backend deliberately does not do that (ticket 08, `ravenna_backend.cpp`).
  The reason is the one place this project's audio path differs from its sibling's: `aes67-sip`
  converts to floats, so its ALSA sample width is invisible downstream, but here `audio.format`
  selects the frame's payload type (`pcm_l24`) *and* the daemon's stream codec (`L24`), and the frame
  carries the device's bytes verbatim (ADR 0001). A silent 16-bit fallback would therefore frame
  16-bit samples as L24 — the wrong audio, with nothing anywhere reporting it. A device that refuses
  the configured format is a commissioning error: change `audio.format`, and the payload type and the
  daemon's codec follow it in one move. **If that trade is the wrong way round, this is the line to
  change** — it was the sibling's behaviour, and it was changed here on reasoning rather than on a
  measurement.
- `period_frames: 48` (1 ms) to match AES67's packet time, `periods: 8`, so the ALSA side keeps the
  AES67 cadence and the wire frame cadence is a multiple of it.
- **No resampling on the AES67 side.** `aes67-sip`'s exact integer-ratio polyphase FIR does not
  transfer: 48k↔16k is a ratio of 3, but two independent 48 kHz domains are **not** an integer
  ratio, so any resampler here carries its own quality claim and needs its own ADR.
- Levels: per-block and per-channel gain/mute with live meters in the UI, mirroring `aes67-sip`.

## Web UI and API

One polling status endpoint plus a configuration document, as `aes67-sip` does it — no websockets,
no SSE. Deliberate, not a limitation to fix: the appliance stays debuggable with `curl`.

In the order an operator meets it: **commissioning preflight** (daemon reachable, RAVENNA device
present, **PTP locked**, link up, measured delay — PTP unlocked is the most common way this
appliance looks healthy while producing silence); **link configuration** (role, peer, mode,
latency, passphrase, block count); **mapping** (block → wire frame block → AES67 stream and
channels, gain/mute); **live status** (delay figure and trend, link statistics, per-block levels,
test signal); **A/V alignment** (the delay offset of decision 8, adjustable while audio runs).

Default REST and UI port is **`:8082`**, deliberately not `:8081`, which `aes67-sip` claims — the
two may share a host during commissioning (open item 10).

House commands, identical in shape to `aes67-sip` so the two projects stay learnable together.

## Code style

C++17, `CMAKE_CXX_EXTENSIONS OFF`, 2-space indent, `#pragma once`, `-Wall -Wextra
-Wno-unused-parameter`. Types `PascalCase`, functions and variables `snake_case`, namespaces
lowercase, one class per header/source pair named after it. No exceptions across module
boundaries. Comment the *why*, in sentences, the way `aes67-sip` does — its comments explain
decisions, not mechanics.

One snippet, chosen because it encodes three of the frozen decisions at once (per-block payload
type for phase 2, one sample position as the sync anchor, and the 8-channel block as the AES67
stream size). **Implemented by ticket 06** — this is the real shape, trimmed to its decision-rich
parts, and `src/wire/frame.hpp` is the authority:

```cpp
// src/wire/frame.hpp
namespace aes67_srt::wire {

constexpr uint32_t k_magic = 0x41363753;  // "A67S"
constexpr uint16_t k_version = 1;
constexpr uint8_t k_max_blocks = 8;
constexpr uint8_t k_block_channels = 8;  // AES67 allows no more than 8 per stream

// The payload type is per block, not per link: that is what lets a link run
// PCM on the blocks that matter and Opus on the rest (docs/ROADMAP.md, phase 2).
enum class PayloadType : uint8_t { pcm_l24 = 0, pcm_l16 = 1, opus = 2, aac_lc = 3 };

struct Block {
  uint8_t index = 0;
  PayloadType payload = PayloadType::pcm_l24;
  uint8_t channels = k_block_channels;
  std::vector<uint8_t> data;  // AES67 payload bytes, verbatim
};

struct Frame {
  uint16_t link_id = 0;
  uint64_t sequence = 0;
  uint64_t sample_position = 0;  // 48 kHz frames since start; every block in a
                                 // frame shares it, so cross-block sync is
                                 // structural rather than reconciled
  std::vector<Block> blocks;
};

}  // namespace aes67_srt::wire
```

**The sizes are decided, not derived on the day.** A frame of eight L24 blocks is **9312 bytes**
(28 header + 8 × (8 block header + 1152 payload) + 4 checksum), which at one millisecond per frame
is the **74.5 Mbit/s** the bandwidth budget assumes; eight L16 blocks is 6240. The test suite
asserts those numbers, so a format change cannot quietly invalidate the budget the whole design
rests on. Byte order is big-endian throughout, with one deliberate exception: L24 payload bytes
stay little-endian `s24_3le` exactly as AES67 delivers them, because reordering every sample twice
would buy nothing.

## Testing strategy

The house framework: `tests/test_framework.hpp`, hand-rolled, no external dependency, runs on any
platform. One `test_<module>.cpp` per module, all linked into a single `aes67-srt-tests`
executable registered with CTest, plus a `config-validate` test that runs the binary against
`config/aes67-srt.dev.conf --validate` — the same two-test shape `aes67-sip` uses.

| Module | What the tests must prove |
|---|---|
| `wire` | Round-trip encode/decode; header and CRC are set before payload; a frame with 8 blocks of L24 PCM is exactly the expected size; unknown version and unknown payload type are rejected rather than guessed |
| `transport` | Loopback over localhost: a frame sent is a frame received; a deliberately starved link raises the delay rather than dropping audio (decision 6, asserted, not assumed) |
| `audio` | The null backend honours the ring-buffer contract; period arithmetic lands on 1 ms at 48 kHz; underrun and overrun are counted, never hidden |
| `daemon` | The fake daemon drives every endpoint the real one has; PTP `unlocked` fails the preflight check |
| `clock` | **Simulated drift**: two clocks offset by a few ppm, run for hours of simulated audio, assert no sample is ever lost or duplicated beyond the designed slip, and that the slip is below the audibility threshold |
| `delay` | Adjusting the offset while audio flows produces no discontinuity above the threshold; the test signal is sample-accurate |
| `control` | Config validation refuses an impossible configuration *before* applying it, with a plain-text reason naming the offending field — the `aes67-sip` behaviour |

**What CI can and cannot do.** GitHub-hosted CI builds and runs all of the above on Linux and
macOS — the null backend, fake daemon and loopback transport mean the logic is genuinely tested
without hardware. **No CI runner can test the things that matter most**: real PTP lock, real
RAVENNA ALSA, real SRT across a real WAN with real loss, and 64 channels at 148 Mbit/s. Those are
manual acceptance checks on hardware at both ends, named in the relevant tickets, and no ticket is
"done" on CI alone.

## Boundaries

**Always**
- Run `scripts/check.sh` (configure + build + ctest + config validate) before committing.
- Validate configuration **before** writing or applying it, and refuse an impossible one with a
  reason that names the field.
- Keep the wire format versioned: a header field is set before the payload it describes.
- Preflight the things that silently produce no audio — PTP locked, daemon reachable, ALSA device
  present — and surface the result in the UI.
- Record a decision in `docs/adr/` when it changes, and update the spec before the code.

**Ask first**
- Changing the wire format's field layout, or the block size and channel ceiling.
- Adding a dependency (each one is a licence and a supply-chain decision).
- Changing the licence, or making the repository public.
- Any change to the SRT latency, buffering or degradation policy — these are decisions 6 and 7,
  not tuning knobs.

**Never**
- Commit passphrases, keys or site credentials.
- Use `TLPKTDROP` to reduce quality, or any automatic quality reduction (decisions 6, 10 and the roadmap policy). Discarding a packet that is already past its play time is not that.
- Fork, vendor or patch `aes67-daemon`; reach it over REST only (decision 11).
- Make the audio path lossy in v1.
- Ship a build without the delay-grows alarm.

## Deployment

Same shape as `aes67-sip`, deliberately:

```
curl -fsSL https://raw.githubusercontent.com/nathanihlenfeldt/aes67-srt/main/scripts/install.sh \
  | sudo bash
```

Idempotent, in order: OS/arch preflight (64-bit Raspberry Pi OS or Ubuntu) → dependencies (libsrt,
ALSA, nlohmann_json, cpp-httplib) → **RAVENNA kernel module via DKMS** (so kernel upgrades rebuild
it) → `aes67-daemon` + systemd unit → this appliance + web UI + systemd unit → real-time sysctls
(the same set `aes67-sip` sets) → PulseAudio disabled → optional ZeroTier → a **preflight report**
naming what will silently fail: PTP lock, daemon reachable, 64ch ALSA device present, SRT port
reachable, config valid.

Shipping GPL-3.0 binaries means source availability is part of distribution, exactly as in
`aes67-sip` — and that is a reason to settle the licence question *before* the installer exists.

### The link it expects

The intended shape is an appliance at the production site and an endpoint in the studio, joined by an
ordinary internet connection. What that connection has to be is a requirement, not a preference,
because 64 channels is **~74 Mbit/s per direction** (about 80 Mbit/s on the wire once SRT, our frame
headers and UDP/IP are counted) — a link that cannot carry that cannot carry the product.

- **Wired Ethernet at both ends.** The studio end especially: Wi-Fi drops bursts that UDP cannot
  recover, and at 64 channels it is the loss the operator hears. Measured, a studio Mac on Wi-Fi lost
  ~6,000 packets in ten seconds.
- **Low jitter, not merely enough bandwidth.** The round trip *plus* its jitter must fit inside
  `link.latency_ms` (default 120 ms). Connections whose latency swings by tens of milliseconds —
  5G/LTE, Starlink and consumer satellite generally — cannot hold that window, and the loss becomes
  audible. They are out of scope for v1, and they are a large part of why phase-2 Opus matters.
- **Roughly 80 Mbit/s per direction, duplex ~160 Mbit/s**, with headroom for retransmission on top.

**The internet is unpredictable, and the design assumes it.** SRT retransmits a lost packet inside the
delay window; a packet that arrives too late to play is discarded rather than stalling the link
(`TLPKTDROP`, decision 6); and when the strain outlasts the buffer the reported delay rises and the UI
alarms past `link.alarm_delay_ms` (500 ms). What the system will not do is pretend a link that cannot
carry the audio is fine — that is what the delay alarm and, later, Opus are for.

### Security, and what it assumes

The appliance is deployed **behind a router or firewall and never takes a public WAN IP**. That is the
assumption the control surface is built on, and it is deliberate rather than an omission: the REST API
and status page are for the site's own LAN, and **exposing them to the internet is not supported**.
There is no authentication and no TLS on the API, and the answer is to not expose it rather than to add
a login page and hope.

In practice:

- **The API is LAN-only.** A site that wants remote management reaches it over a VPN or tunnel
  (ZeroTier, WireGuard, an SSH port-forward) — the tunnel carries the authentication, not this program.
- **The SRT link between site and studio carries a passphrase.** It is the one part of the product that
  crosses the public internet, and it is encrypted even though both ends sit behind firewalls; the
  measured cost is about 1% of one Pi core at 148 Mbit/s (`docs/research/libsrt.md`). A site that
  cannot share a secret has a link it should not run.
- **If the API must be internet-facing**, this assumption is broken and open item 1 reopens: the choice
  is a tunnel (preferred) or real authentication and TLS, which does not exist yet.

It is stated here, in the installer's output and in the runbooks, because a security property that
lives only in someone's head is not one.

## Non-goals

- **No lossy encoding in v1.** It is roadmap phase 2 (`docs/ROADMAP.md`), and the wire format
  carries the payload type so phase 2 is an addition, not a format break.
- **No video transport.** We provide the audio-side delay to match someone else's vision.
- **No redundancy or bonding**: no SRT stream groups, no 2022-7, no dual links, no hot spare.
- **No fan-out.** One link per appliance; several links later.
- **No talkback, IFB or monitoring mixes.** There are no humans in the audio path.
- **No non-AES67 audio**: no SIP, no analog, no codecs on ingest.
- **No sample rate other than 48 kHz.**
- **No PTP tunnelling**, and no attempt to lock the two ends' clock domains to each other.
- **No macOS or Windows runtime target *for the appliance***; macOS is a development environment
  only. (A *second product* — a macOS application bridging SRT to CoreAudio, sharing this code's core
  — joined the roadmap on 2026-09-16; see `docs/ROADMAP.md` and ADR 0004. This line is about what
  *this* program runs on, and it still runs nowhere but Linux.)
- **No NMOS, RTSP or RAVENNA-specific extensions** beyond what the daemon already exposes.

## Open items (need answers before commissioning)

1. **UI authentication and transport security** — **resolved by the deployment assumption.** The
   appliance sits behind a firewall and never takes a public WAN IP, so the API is LAN-only and the
   link is encrypted with a passphrase (see *Security, and what it assumes*). It **reopens** the moment
   someone needs the API reachable from the internet; the answer there is a tunnel, or the
   authentication and TLS this program does not have.
2. **Licence** — **resolved**: GPL-3.0, ADR 0002, with `LICENSE` in place. libsrt turned out to be
   MPL-2.0 and to oblige us to nothing, so this was a choice rather than a constraint
   (`docs/research/libsrt.md`); GPL-3.0 was chosen for consistency with `aes67-sip` and for
   GPL-compatibility later. Distribution carries the source-availability obligation — ticket 15's
   concern, and no longer blocked on a question.
3. **Repository visibility.** The installer command above assumes public, as `aes67-sip` is. Bare
   `aes67-srt` is currently private; making it public is an *ask first*.
4. **Is there a PTP grandmaster on the AES67 VLAN at both ends**, and what PTP domain does each
   end use? Without lock, no audio, so this is a commissioning blocker.
5. **How far-end devices subscribe to our streams**: SAP/RAVENNA discovery, or hand-configured
   multicast address and port? (Unchanged from `aes67-sip`'s open item 3.)
6. **Static IP / DHCP reservation** for the appliance on the AES67 VLAN at each end.
7. **Maximum delay range for the A/V delay line**, which is set by how slow the vision path
   actually is. 0–2 s and 0–5 s are different products.
8. **What carries vision**, and its measured end-to-end latency — this decides whether our 100–200 ms
   transport leaves enough headroom to align.
9. **ZeroTier: still wanted?** `aes67-sip` uses it for NAT-free SIP; SRT handles NAT and
   rendezvous itself. It may still be wanted for management access.
10. **Our REST/UI port.** 8082 is proposed so the appliance can coexist with `aes67-sip`'s 8081.
11. **The far end's 64 channels**: which devices, and is the block→stream mapping per-site
    configuration or fixed by convention?

**The field procedure that walks items 4–6 and 11 is `docs/runbooks/commissioning.md`**: it states the
block-to-stream convention, what each end must have, and the checks to run on a real site and studio.

## Verification needed before implementation

These are the things that must be **read or measured**, not decided. Everything else in this spec
is decided.

1. **libsrt** — **done, ticket 02 (issue #2)**: `docs/research/libsrt.md`. Licence verified (MPL-2.0,
   obliges us to nothing); message boundaries and the live-mode 1456-byte ceiling established;
   latency defaults and the fact that latency is *negotiated* understood; the passphrase rule
   confirmed against the header; the statistics the UI needs identified; and bonding found to be
   compile-time gated and rendezvous-incompatible. Three things it could not settle moved to ticket
   07: the late-arrival behaviour decision 6 rests on, the CPU cost of encryption at 148 Mbit/s, and
   buffer sizing. **Encryption has since been measured on the Pi** — ~1% of one core at 148 Mbit/s
   (`docs/research/libsrt.md`) — so the late-arrival behaviour and buffer sizing remain.
2. **The clock module** — **done, ticket 02 (issue #3)**: `docs/research/clock-recovery.md` and
   **ADR 0003**. Continuous resampling costs **11.27% of one Pi 5 core** at 64 channels and +10 ppm,
   where a slipping design would need **1700 corrections an hour** at 2.02-second intervals. The
   largest technical risk in the project is closed, and the audibility question is *dissolved* rather
   than answered: with no corrections there is nothing to make inaudible.
3. **`aes67-daemon` at 64 channels** — **mostly measured**: `docs/research/aes67-daemon-64ch.md`.
   `plughw:RAVENNA` takes **64 channels of `S24_3LE` at 48 kHz** and opens; PTP is locked; the daemon's
   frame size is 48 (the 1 ms period this spec specifies); and its config, PTP, sinks, sources and
   discovery endpoints are recorded. **What remains is the per-stream mapping** — which AES67 stream
   carries which device channels — which cannot be seen with no sinks configured and is handed to
   ticket 09, where a sink is created for real.
4. **Opus** — confirm 48 kHz native, the multistream/channel-mapping API for 8-channel blocks, and
   real latency figures. Phase 2, but the `PayloadType` enum depends on the answer. Ticket 04, issue #5.
5. **RAVENNA DKMS on the target Pi** — a re-verification, since `aes67-sip`'s installer already
   does this successfully; confirm for the Pi model actually being bought.
